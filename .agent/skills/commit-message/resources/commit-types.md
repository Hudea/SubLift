# Commit Types 速查与避坑指南

如果对当前的提交改动属于什么类型有疑问，参考本指南进行匹配。

| Type | 场景 | 典型描述动词 |
|:---|:---|:---|
| `feat` | 新增一个功能、特性、页面或对用户可见的新选项 | 新增、实现、支持 |
| `fix` | 修复一个已知或未知的缺陷、崩溃、UI错位等非预期行为 | 修复、解决 |
| `docs` | 仅修改 README、内联注释、使用说明，对代码逻辑无任何影响 | 补充说明文档、修改注释 |
| `style` | 仅修改代码格式（空格、缩进、漏分号、排序），不改变任何逻辑 | 格式化、统一代码风格 |
| `refactor` | 重构代码逻辑（重命名变量、提取公用函数、拆分组件），既不修 bug 也不加新功能，但改变了内部实现 | 重构、抽取、重命名 |
| `perf` | 专门为了提升性能、降低内存占用、减少打包体积而做的代码调整 | 优化性能、降低延迟 |
| `test` | 新增或补全遗漏的单元测试、集成测试、快照更新，不涉及业务代码改动 | 补充测试、更新快照 |
| `build` | 影响构建系统或外部依赖的改动（如 webpack/vite 配置、npm 依赖升级） | 升级依赖、调整构建配置 |
| `ci` | 针对 CI/CD 配置文件和脚本的修改（如 GitHub Actions、GitLab CI） | 更新CI流程 |
| `chore` | 构建过程或辅助工具的变动（构建脚本更新、包管理器缓存更新等），或无法归入以上的琐事 | 清理冗余代码、调整忽略文件 |
| `revert` | 专门用于撤销之前的 commit 操作 | 撤销提交 |

---

## ⚠️ 常见判断陷阱与建议

### 1. `refactor` vs `style`
- 如果你改了**逻辑流转、文件结构、函数拆分**，必须是 `refactor`。
- 如果你只是用 Prettier 跑了一下**格式化，加了点空格、换了引号**，必须是 `style`。
- **不要混淆**：不要把“优化代码可读性”的重构称为 `style`，这很危险。

### 2. `feat` vs `refactor`
- 如果这个改动**带来了新的用户感知能力**或功能入口，是 `feat`。
- 如果纯粹是为了让未来的扩展更容易，而**当前用户感受不到变化**，是 `refactor`。

### 3. 一次提交内有多个类型
- 按**最重要/最大范围**的目的分类。
- 比如：开发新功能顺便写了该功能的测试 -> 选 `feat`，而不是 `test`，因为核心目的是新特性。
- 比如：修复 Bug 顺便重构了一下周围的代码以防再次出错 -> 选 `fix`。
- **但是**：如果两者毫不相干（比如加了一个新 API，同时改了另一个老界面的样式），应该在输出中强烈建议**拆分**。

### 4. `chore` 是个筐？
- 尽量避免滥用 `chore`，如果能更明确是 `build` 依赖升级，或者代码清理的 `refactor`，优先用更具体的类型。
