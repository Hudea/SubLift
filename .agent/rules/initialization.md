# Initialization 规则

> `./init.sh` 是会话开始或恢复工作前的项目初始化入口。它只回答：当前 Harness 与项目环境是否具备可靠开工的最低条件。

## 职责

`init.sh` 可以检查或建立：

- Harness 连续性入口是否可读取；
- 项目必需工具链是否可用；
- 项目依赖是否已安装并与依赖声明一致；
- 必需配置和本地环境是否具备；
- 最小启动、最小编译或测试框架冒烟是否可通过。

失败项必须能够说明：当前会话为什么无法可靠开始开发或执行局部验证。

## 边界

`init.sh` 负责建立工作前提，不负责证明产品可以交付。

不得加入：

- 全量测试、全量 lint 或完整类型检查；
- 发布构建、E2E、性能测试、安全扫描或跨平台验证；
- 当前 Feature 的专项验收；
- 产品行为正确性验证；
- `.agent/` 能力包的全量文件审计；
- 仅为了「更保险」而重复 CI 或 Verification 已承担的工作。

这些检查应放入 Testing、Verification、独立脚本或 CI。

## 冷启动与热启动

允许冷启动做必要的较重操作；热启动必须避免无条件重复。

- **冷启动**：依赖缺失、依赖声明变化、工具链变化、配置变化或初始化缓存失效；
- **热启动**：相关输入未变化，已有项目基线仍然有效。

昂贵检查必须有明确失效条件。不得在每次会话启动时无条件安装依赖、完整构建或运行大范围检查。

## 新增检查的准入条件

向 `init.sh` 新增检查前，必须能够回答：

1. 它验证或建立了哪项开工前提？
2. 它失败时为什么不能继续可靠工作？
3. 它属于冷启动还是每次启动？
4. 它由什么变化触发失效？
5. 为什么不能放在 Testing、Verification 或 CI？

无法明确回答以上问题的检查不得加入。本规则不规定具体安装/构建/冒烟命令；那些是实例化后的实现选择，本规则只规定其准入资格。

## 实现约束

- 初始化应当幂等；
- 不得修改产品源代码或进度状态；
- 不得隐藏失败或自动绕过错误；
- 输出应指出失败项以及恢复基线所需的下一步；
- 项目专属逻辑可以存在，但必须遵守本规则；
- 修改 `init.sh` 或本规则属于 Harness 变更，不应夹带在普通产品 Feature 中。

何时调用、失败后怎么办：见 `session-bootstrap` / `session-handoff`。
