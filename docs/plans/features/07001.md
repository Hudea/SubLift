# Feature 计划：新 Harness 体系迁移

## 目标

在不改变 SubLift 产品运行时的前提下，实例化新 Harness：以 `phases.json` 管理当前 Phase、以
`.agent/` 管理后续协作流程、以秒级 `init.sh` 提供 L0，并保留可执行的完整产品验证门与旧追踪兼容。

## 范围

- 引入 canonical `.agent/` 及其 validators/self-test，实例化 `AGENTS.md`。
- 新建 Phase index 和 Phase 7，保留 legacy phase detail/`feat-*` 记录并以兼容 schema 承接。
- 将 `phase4.1.json`、`phase4.2.json` 规范为 `phase41.json`、`phase42.json` 并修复精确引用。
- 将原标准门迁入 `scripts/verify-standard.sh`，新 `init.sh` 只做 L0，并支持显式标准/旧环境变量转发。
- 改造 benchmark repo-root marker 并添加新标记/legacy fallback 的回归覆盖。
- 更新用户可见文档、决策、progress 与 Phase 7 evidence。

## 非目标

- 不改动 CLI、IPC、OCR、C++/Swift build、质量基线或发布策略。
- 不重写历史 feature ID/evidence、不删除 `feature-list.json`、`.grok/` 或现有 adapter。
- 不创建伪造的 Harness state、review receipt 或 commit；不提交、不推送。

## 验收标准

- [ ] `./init.sh` 通过 L0，`phases.json` 的全部 detail_file 可读；`./init.sh --standard` 可显式转入完整验证。
- [ ] Phase 1–6 历史 detail 和 Phase 7 canonical detail 均可由兼容 schema 表达，且旧小数路径的实际链接均已迁移。
- [ ] `.agent` 自测与 Project validators 可运行，AGENTS 说明 Codex receipt 不伪造 adapter 的边界。
- [ ] 只有 `phases.json` 的 root 与只有 `feature-list.json` 的 legacy root 都可解析 benchmark manifest。
- [ ] `scripts/verify-standard.sh` 实际通过，确认原日常产品门未丢失。

## 架构依据

- `docs/plans/architecture/harness-migration.md`：确立 legacy/canonical schema 分支、L0/标准门分层与不改产品运行时的边界。
- `src/sublift/benchmark/config.py`：现有 root marker 与兼容行为的唯一实现入口。
- `AGENTS.md`：项目级验证、Git 授权与后续 Harness 调度契约。

## 实施步骤

### 1. 引入 Harness 和 Phase 索引

- 位置：`.agent/`、`AGENTS.md`、`phases*.json`、`docs/phases/`
- 行为：复制新 Harness，建立 Phase 1–7 索引和明确的 legacy/canonical Phase detail schema；保留 `feature-list.json` 为兼容视图。
- 依赖：无。
- 验证：L0、JSON parse、Phase detail 数量与 legacy ID count 前后保持一致。

### 2. 划分 L0 与标准产品验证

- 位置：`init.sh`、`scripts/verify-standard.sh`
- 行为：新的默认 init 仅做文件/JSON/index 检查；原 full gate 原样迁入独立脚本，`--standard` 与历史 env flag 明确转发。
- 依赖：步骤 1。
- 验证：计时 L0、检查其无 `uv sync`/CMake/pytest 输出；完整标准脚本通过。

### 3. 接线新旧项目索引

- 位置：`src/sublift/benchmark/config.py`、`tests/test_benchmark_*.py`、`tests/test_roi_output_path.py`
- 行为：root discovery 接受 `phases.json` 优先 marker，保留 `feature-list.json` fallback；fixtures 覆盖新 marker，新增 legacy fallback 回归。
- 依赖：步骤 1。
- 验证：聚焦 pytest 覆盖两种 marker，静态检查无回归。

### 4. 文档与交付记录收口

- 位置：README、Architecture、Decisions、progress、Phase 7。
- 行为：记录迁移边界、验证命令、历史兼容原则和最终 evidence；不保留活动 state。
- 依赖：步骤 1–3 和验证结果。
- 验证：链接检索、L0、自测、标准验证。

## 测试模式

- `test_mode`：`posthoc`。本 Feature 是 Harness bootstrap；开始时没有可用的 Harness Feature state，benchmark marker 的新自动化回归在实现中补建，不能声称已经跑过 test-first RED。
- 实现后补建：`phases.json` primary marker 和 `feature-list.json` fallback 的 manifest path-resolution 测试。

## 验证方案

```bash
./init.sh
python3 -m unittest discover -s .agent/tests -v
uv run pytest tests/test_benchmark_config.py tests/test_benchmark_matrix.py tests/test_roi_output_path.py
uv run ruff check .
uv run mypy src tests
./scripts/verify-standard.sh
```

- 正常路径：新 Phase index、L0、root marker 和完整标准门均通过。
- 边界条件：legacy root 没有 `phases.json` 时仍解析；`phase4.1/4.2` 的正文只保留一份 canonical 文件。
- 错误路径：不存在 detail_file 或无 index marker 的 manifest 不被误判为仓库根。
- 回归范围：Python benchmark 配置、Harness JSON/index 和原 C++/pytest/parity 标准门。

## 风险与假设

| 类型 | 内容 | 处理方式 |
|---|---|---|
| 风险 | legacy schema 意外让新任务使用旧格式 | legacy 分支只接受冻结的 Phase 1–6 metadata，后续 Phase 只能使用五位 ID 的 canonical 分支 |
| 风险 | L0 被误认为完整 CI | AGENTS / README 明确标准验证脚本并保留 `--standard` 转发 |
| 假设 | 历史 `feature-list.json` 仍需存在 | 保留根文件并保留 fallback 测试 |
| 风险 | Codex 没有模板 adapter | 不伪造 attestation；仅记录实际可追溯的 Codex 委派 |

- 用户必须决定：删除历史记录、修改产品协议/依赖/发布策略、commit 或 push。
- 停止条件：需要重写历史 evidence、删除旧 adapter、触碰产品运行时或验证依赖不可用外部资源时。
